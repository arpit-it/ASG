# Automated Software Generator project conventions

The Flutter application root is `asg/`. Run Flutter commands there. ASG targets Android, iOS, web, macOS, Windows and Linux; distinguish included runners from verified platform/device behavior. Managed MLX setup and the current independent Flutter web generator host are macOS-specific, not the overall product.

Read and follow [the project coding standards](asg/docs/development/CODING_STANDARDS.md) before working on this repository. This is the canonical instruction document for Flutter style, MVC boundaries, async work, storage, UI, testing, and completion checks. Direct user instructions take precedence; preserve unrelated changes.

Use MVC for new application features and files:
- `lib/models/`: typed domain data and pure validation/serialization. No Flutter widgets, HTTP clients, or storage plugins.
- `lib/views/`: screens and reusable UI. Keep layout, rendering, navigation, and text/form controller lifecycle here. Delegate application actions to controllers; do not send HTTP requests, serialize stored records, or use preferences directly.
- `lib/controllers/`: application state, validation/workflow coordination, loading/error state, and controller actions. No widgets, BuildContext, dialogs, or navigation. Dispose listeners and cancel owned work.
- `lib/services/`: storage, local model transport, folder picker, execution policy, and other platform/external integrations. Inject services/providers into controllers for deterministic tests.
- `lib/main.dart`: bootstrap and top-level error presentation.

Use one controller per feature and split screens into focused view files. Avoid recreating a single large UI file. Keep business rules out of widget callbacks. Preserve existing preference keys and JSON formats unless an explicit migration is implemented.

The fixed Flutter web generator uses the same MVC separation; see asg/docs/architecture/GENERATION.md for actual supported behavior and safety limits. Do not describe this initial template slice as arbitrary model source synthesis. Other future framework adapters should map these responsibilities idiomatically.

Validate with `flutter analyze`, `flutter test`, and a relevant platform build. Architecture tests in `test/architecture_test.dart` guard core import boundaries. Add controller tests for error handling, persistence ordering, and async disposal when changing workflows.

## GitHub issues, branches and pull requests

Use direct issue-based branch names such as `<issue-number>-<short-description>` without `codex/`, `chatgpt/`, or any assistant/provider identification. Do not add Codex, ChatGPT, OpenAI, or similar identification to branch names or PR titles/bodies. If a working identity is needed, use exactly "ASG is working". Do not announce routine branch creation. This user preference applies to all future and scheduled runs; historical branch names remain unchanged.

Repository: `https://github.com/arpit-it/ASG.git` (`origin`). The user authorized publishing the reviewed existing baseline directly to `main` once, tracked by issue #1. After that initial publication, use the following workflow for every new implementation, bug fix or scheduled development increment:

1. Read or create a GitHub issue before implementation. Record the problem, scope, acceptance criteria and validation plan. Reuse an existing issue instead of creating duplicates.
2. Inspect `git status`, staged changes, branch and remote state. Use the connected GitHub plugin to inspect current remote main, then safely synchronize local refs before integration. Preserve unrelated edits; do not discard, reset, auto-stash or stage someone else's work.
3. Create an issue-linked branch named `<issue-number>-<short-description>` from current main in an isolated registered worktree. Concurrent writers follow the ownership and integration rules below; never share a writer checkout or implement directly on `main`.
4. Implement a coherent, testable user outcome following MVC and CODING_STANDARDS.md. Keep related behavior and necessary failure handling in one reviewable increment instead of splitting every method into its own PR. Immediate security/regression fixes may remain narrowly focused. Add relevant regression tests; the integration owner updates shared project memory/progress. Keep model weights, virtual environments, credentials, build output and local IDE caches out of commits.
5. Review `git diff` and `git diff --cached`, run format/analyze/tests and appropriate builds, then commit only related paths with a descriptive conventional commit message. Link the issue in the commit or PR.
6. Publish the feature branch through the connected GitHub plugin, verifying its tree matches tested contents. Open a PR targeting `main`, with a concrete behavior summary, linked issue (`Closes #<number>` when complete), tests and material limitations. Use a draft PR if incomplete. Attach created PRs to the current task when the app's PR attachment tool is available. All GitHub reads/writes and protected merges use the connected plugin; do not fall back to terminal push, authentication setup or browser publication.
7. Keep the issue and PR updated. Merge through the PR, following required checks/review. The user now authorizes an independent reviewer agent to merge PRs after approving the final revision and confirming required checks pass. The implementing agent must not self-approve or bypass that independent review. After a merge, fetch and fast-forward local `main` only when safe; verify the remote result before claiming completion.

The user's authorization covers in-scope issue creation, branch creation, commits, feature-branch pushes and PR creation; do not repeatedly request permission for those routine steps. Never force-push shared branches, rewrite published history, bypass branch protection, or push unrelated files. Rebase only unshared local work unless otherwise authorized; use `--force-with-lease` solely when a necessary private-branch rewrite has been explicitly agreed. Never use an unconditional force push.

These rules also apply to the 15 minute automation. Read `asg/docs/REQUIREMENTS.md`, `asg/docs/history/AGENT_MEMORY.md` and `asg/docs/history/PROGRESS.md`, select the next open issue, and use its dedicated branch/PR. Publishing source is not a claim that a production application has been deployed; obtain a concrete release/deployment target before provisioning or publishing external services.


## Scheduled issue selection and independent review

At each 15 minute run, inspect current app status, open issues/PRs and coordinator ownership. Resume owned in-progress work first. A second dependency-ready, nonoverlapping writer may proceed only under the coordinated parallel policy below; it does not bypass requirement priority or blocked prerequisites. Reuse an existing issue whenever suitable; create at most one necessary, narrowly scoped new issue per run only when no existing issue covers a real gap. Do not invent issues or expand a speculative backlog. Complete implementation, test, fix discovered defects, and retest before moving on. Keep genuinely blocked work open with clear evidence rather than pretending it is finished.

The user explicitly requests and authorizes reviewer-agent delegation. After opening a PR, spawn an independent reviewer agent to inspect that PR's exact final diff, acceptance coverage and real CI/test results. The implementer must resolve blocking findings, retest affected behavior and request re-review if the diff changes. The reviewer is authorized to merge into main only after approving the final revision and confirming all required checks pass. Never self-approve, bypass protection or merge a failing PR. Verify the remote merge and issue closure; update memory and safely fast-forward the local main checkout.

## Coordinated concurrent development — owner-authorized 5 November 2026

This policy supersedes older one-active-issue wording only for dependency-independent work admitted by the coordinator. [Parallel development](asg/docs/development/PARALLEL_DEVELOPMENT.md) defines the operational procedure and [execution contract](asg/docs/development/execution_contract.example.json). It is an execution policy, not another backlog.

- Maximum **two concurrent writers** per local repository, each in a different registered worktree with an issue/track, owner, valid lease and exclusive literal path scope. Claim before editing through `asg/tools/development_coordinator.py`; same-task, overlapping scope and third-writer claims fail closed. Read-only researchers/test designers may work in parallel; avoid creating duplicate issues. Subagents inherit permissions and do not establish a separate security boundary.
- Record a compact contract with requirement ID, observable user outcome, dependency evidence, owned paths, acceptance examples, representative failure cases and validation plan. A dependent feature waits for its prerequisite's verified merge. A parent issue may have disjoint implementation tracks whose changes integrate into one coherent PR; only the integration owner edits shared requirements, history, manifests and workflow policy.
- The coordinator/orchestrator remains read-only while both writer slots are occupied. It may implement only after acquiring an available writer slot. Writers stop edits before handing their changes to the integration owner; final reviewer remains independent of implementation.
- Leases are cooperative, same-host coordination. Expiration blocks new work until explicit reconciliation; never steal a claim merely because its clock expired. Inspect owned processes, worktrees, dirty state and remote effects first. Preserve abandoned work and record recovery evidence. Do not use separate clones to evade coordination. Cross-host writers require a shared coordination service and are not enabled by this local tool.
- Serialize integration and merge with the coordinator's integration lock. Re-read remote main, integrate without overwriting changes, verify final source identity, run required checks and obtain fresh independent review for the exact final revision. A changed head/base invalidates prior integration evidence. Local attestations never replace GitHub branch protection or prove remote authorization.
- Layer feedback: focused tests during editing, broader relevant regression checks before publication, then every required check on the final revision. Existing required checks stay mandatory. Reuse evidence only for unchanged inputs and only where an explicit verification policy permits it. Never reuse a live model/device result as evidence for another revision or host.
- Serialize live inference against the existing single-worker model. Treat a live runtime, native build output, preview port and shared artifact directory as exclusive resources assigned by the integration owner; do not launch competing live tests or builds against them. Independent disposable fixtures may run concurrently within measured host capacity.
- Record task-to-merge time, CI observation wait, review rework, escaped defects and verified user outcomes with evidence. Unknown values stay unknown; manual observations and measured local durations remain distinct from provider-reported CI timing. PR count is not delivered capability. Use more reasoning for ambiguous architecture/security/review and lighter effort for bounded discovery; check actual results rather than assuming a model choice guarantees quality.

## Repository safeguards

Main is protected with required PRs, the Flutter checks and web build / Python runtime fixtures checks from GitHub Actions, up-to-date branches and resolved conversations. Admins cannot bypass; force pushes/deletion are off. Do not weaken controls to merge. All external fork workflows need approval: inspect submitted code and workflow/dependency changes before approving execution. Never approve unknown code automatically. CODEOWNERS requests owner review; the reviewer agent shares the owner's GitHub identity, so its independent verdict is not a second GitHub approver. Required GitHub approval count remains zero until another trusted account exists.

Preserve read-only workflow permissions and disabled Actions PR-approval permission. The Actions allowlist permits owner actions, GitHub-created actions and subosito/flutter-action@1a449444c387b1966244ae4d4f8c696479add0b2; coordinate reviewed workflow upgrades with the allowlist. Keep visibility unchanged unless the owner explicitly requests a change. See CONTRIBUTING.md and SECURITY.md.


## Canonical documentation and scheduled task queue

The sole requirements and task file is `asg/docs/REQUIREMENTS.md`. Read it on every 15 minute run, together with `asg/docs/history/AGENT_MEMORY.md` and `asg/docs/history/PROGRESS.md`. Follow its new-task, deduplication, dependency and completion rules. Add justified new tasks there with stable IDs and acceptance criteria; do not maintain another backlog in roadmap, contracts or memory files. Resume active work first; admit a second independent track only under the concurrency policy above. Finish and verify prerequisite merges before selecting dependent work. Check Done only after acceptance, relevant checks, independent review and verified remote merge; record PR and merge SHA. Shared ledger/history edits belong to the integration owner.
