# Independent Flutter source generation

## Current slice

ASG is a Flutter application targeting Android, iOS, web, macOS, Windows and Linux. Included platform runners do not establish tested device support. Managed MLX setup and the current independent Flutter web generator host are macOS-specific; other platforms retain supported app features and runtime connection controls.

Before opening generation, use Discuss, Plan and Review to save a current Plan explicitly scoped to the fixed starter. Inspect its validated four-task preview and approve it. Build rereads this exact approval against current project metadata, requirements-board revision and prototype revision/definition; stale, withdrawn, unapproved, legacy or malformed contracts cannot start. The generation form then requires separate operation consent. Approval alone does not authorize source edits; reviewed candidates require separate preparation, confined verification and promotion consent below.

On macOS, open a saved project's preview and choose **Generate Flutter source** (code icon). Review the current requirements/prototype, choose an existing parent directory, a new lowercase folder name, an initialized Flutter SDK directory and an installed Python 3 executable. Explicitly approve the listed operations, then choose **Generate, test and build**.

The generator writes a fixed, portable Flutter web MVC starter: typed model, observable controller, view, bootstrap, independent tests, JSON application data and requirements metadata. User/model text is serialized only into JSON data, never executable Dart/HTML or dependency declarations. It supports the existing headings, text, tasks/completion, counters, notes and bounded button actions. Initial creation remains fixed. Approved tasks can subsequently request reviewed, bounded Dart replacements through the candidate workflow below; other frameworks/native runners remain unavailable.

Saved generation outcomes now identify whether their recorded application/project inputs match the current screen, represent an earlier snapshot, or cannot be identified. Earlier/unknown builds have explicit preview/open labels. This compares recorded input fingerprints; source/output integrity is still checked separately before preview. Later chat or interaction edits require a new folder to export, while an earlier verified build remains available for explicit preview. Existing v1 history stays readable without migration.

The default chat/right-hand preview remains ASG's interpreted prototype. Generated source is a separate snapshot; later chat edits require generation into another new folder. Existing projects are never regenerated in place or overwritten. Generated-app interactions are session-only; ASG's own prototype remains durable.

## Verification and preview

Only these fixed operations run, with argument arrays and no shell command interpolation:

1. flutter --no-version-check pub get --offline
2. flutter --no-version-check analyze --no-pub
3. flutter --no-version-check test --no-pub
4. flutter --no-version-check build web --no-pub --no-web-resources-cdn

Each operation has a 180-second deadline and a 64 KiB combined stdout/stderr byte limit. Output beyond that limit terminates the owned process group and records `outputLimitExceeded`, even if the command already exited zero; exactly 64 KiB is permitted. Captured diagnostics remain bounded. This outcome blocks subsequent operations and cannot yield Ready. The trusted Python helper starts an owned process group, terminates it on timeout/parent exit/disposal, and escalates termination when needed. A macOS empty-group permission response after root exit is not treated as a failed Flutter command; live-root termination failures still surface. This trusted starter path provides lifecycle management, not an OS security sandbox. Model-written candidates instead use the confined runner described below.

The SDK must already have its tools snapshot, Dart executable and package configuration. Offline resolution uses existing pub-cache packages. Analytics/version checks are disabled and Flutter's artifact-download base points to an unavailable loopback mirror so missing SDK artifacts fail rather than silently downloading. The trusted starter path has no network isolation guarantee. The installed SDK/Python and cached packages are trusted; candidate commands receive the narrower sandbox below. No system software, model weights or third-party application package is installed by this flow.

Only a successful analyze/test/build can produce a ready result. **Start actual built preview** serves the fingerprinted web build on loopback with a fresh unpredictable URL prefix, no directory listing/source serving and cross-origin asset restrictions. **Open generated app in browser** opens that local URL explicitly. Closing the setup screen stops its owned server. Opening a browser URL alone is not proof that all application behaviors work.

## Boundaries and recovery

Parent/SDK paths are canonicalized, symbolic-link aliases rejected, and a single new directory is created exclusively. Template files use exclusive creation. Source files and generated output are fingerprinted. Verification checks source before stages; dependency lock/package configuration/graph fingerprints are captured after resolution and checked before later commands and retries. Source or critical metadata changes stop verification instead of executing changed inputs. Output changes prevent/reject preview serving.

Outcomes, step exit codes/output and failures are stored transactionally under studio.generation.v1.<projectId>. Exceptions after preparation persist a failed outcome; failed history writes preserve previous durable history. On reopening, interrupted verification is displayed honestly. Retry runs the saved verification sequence on unchanged source and metadata; corrected SDK/Python selections can be explicitly supplied. An interrupted resolution without a durable metadata snapshot requires a new folder. Partial generation folders are retained; generation failure never silently deletes/replaces them. Initial starter generation does not repair source automatically. A separately consented bounded candidate-repair session is available after a recorded candidate failure; see the F05 sections below.

Build/.dart_tool caches are generated tool-owned data, not a security boundary. These checks do not defend against a malicious same-user host racing filesystem changes, modifying the installed SDK/Python/pub cache or database, or tampering with compiler internals. Do not use this feature to execute arbitrary downloaded/untrusted projects. Native concurrent app processes are outside the storage contract. The installed stable ASG app is not replaced.

## Validation

Native-host tests run on macOS/Linux; unsupported hosts retain controller/fallback tests and do not claim local generation support. Regular tests cover traversal/existing paths/symlinks/concurrent entries, hostile text as data, failed verification/retry, changed dependency metadata/output, preview scope, approval, duplicate submission, disposal, late server cleanup, durable exception recovery and UI outcome states. Python fixtures cover bounded output, nonzero exits, process-group timeout/descendant cleanup and macOS exited-group behavior.

The opt-in real test creates a new temporary project, runs actual offline resolution, analysis, generated widget tests and a web build, then checks served compiled output:

```sh
ASG_FLUTTER_SDK=/path/to/flutter flutter test test/source_generation_test.dart --dart-define=ASG_REAL_GENERATION=true --plain-name 'real independent generated Flutter project'
python3 -B tools/test_generation_command.py
```

CI runs the real generation test after warming the SDK/cache with the main app's checks/web build. The Qwen inference test remains separately opt-in; generation uses the current validated definition and does not invoke the model.

## Editing project requirements

The workspace's **Edit project details** action updates the saved name and requirements for future exports. It preserves project identity, platform/type/location and the current prototype/chat/revision. A starter that has never been saved is persisted before metadata changes, so restarting does not regenerate it from revised requirements. Failed writes retain input for retry; stale, missing or duplicated project records require reopening details. Existing exports remain immutable and compare as outdated when their requirements fingerprint differs. Change the actual prototype through chat, then export into a new folder.

## Dashboard outcomes

Project cards read the latest saved generation record and show no snapshot, unverified source, unfinished verification, saved verification success, failure or unreadable history. Input fingerprints distinguish current/earlier/unknown snapshots. Corrupt application data leaves saved build evidence visible with unknown input match; one unreadable history record does not break other cards. Returning from a standalone project refreshes the summaries. These are read-only saved outcomes, not live process status or filesystem verification. Dashboard cards summarize the latest working outcome; the separate F06 history retains timestamped outcomes and last-successful-version evidence and offers explicit inspected rollback. A latest-outcome card alone does not establish that historical artifacts remain available. Opening the generated preview still checks artifacts through the existing guarded workflow.

For already-migrated databases, unreadable application/generation records are retained verbatim and raise an explicit per-key error, so other projects remain accessible after restart. Invalid migration/global data and physically corrupt database files still fail startup. This does not provide automatic record repair or recovery of damaged bytes; see STORAGE.md.

## Plan and task provenance

The version-1 `asg-build` contract accepts only `flutter-starter` and its canonical resolve → analyze → test → build graph. Version 2 maps bounded unique task IDs to exactly one of each of the same four operations, listed in topological order. Dependencies must name earlier tasks; analyze/test require resolve transitively and build requires both analyze and test transitively. Analyze and test may run in either approved order; execution remains sequential and every check is mandatory. IDs use `[A-Za-z][A-Za-z0-9_-]{0,63}`. Saved graph order drives execution, history validation and task status; retry compares the complete graph with the exact approved contract before stopping preview or invoking the host. Version 3 adds a required `boardTaskId` on every task, referencing four distinct existing tasks in the current structured requirements board. Each board prerequisite must also be mapped and occur transitively before its dependent; a manually Done prerequisite cannot substitute for a mapped operation. Missing/duplicate/mixed references and references on versions 1/2 are rejected. Build and retry reread the board before host effects and at execution authorization boundaries; the approval already binds its revision. Saved graphs retain these references and show them beside actual operation status after reopen. Board links are provenance, not automatic task completion or verification of requirement acceptance; the board is not changed by execution. Version 4 permits several operations to reference the same board task, so a single starter-workflow task needs no artificial split. Every operation mapped to each board prerequisite must precede every dependent operation transitively; missing prerequisites remain invalid even when manually Done. Version 3 retains distinct references. All versions keep the same four mandatory operations and reject command text or custom source edits. Duplicate JSON members (including escaped equivalent names), unknown fields/operations and ambiguous fences fail closed. Saved outcomes retain exact approval identity and task graph; task states are pending, running, passed, failed, blocked or interrupted based on actual results. Retry requires the same approval identity and matching inputs, not a replacement approval for old source. General `asg-tasks` proposals are planning data only and cannot execute commands. Safe-boundary checkpoints/resume are described below.


Command results now retain `cancelled` separately from timeout and output exhaustion. SIGTERM/SIGINT or observed parent loss makes a helper result fail even if the child exits zero. Legacy saved results omit this field and read as false. This records cancellation evidence when a result reaches storage; process teardown or application death does not guarantee a final saved result. User Stop and safe-boundary resume are implemented as described below.


## Explicit safe-boundary resume

Verification writes additive `checkpointVersion: 1` evidence before dispatch. Resume remaining checks requires separate operation consent, the exact current approval/task graph and prototype/project/board inputs, and the saved SDK/Python settings. Source and dependency fingerprints are revalidated before remaining work. A successful prefix is retained; only its unexecuted suffix is dispatched, with the existing awaited pending marker and result protocol. The fixed graph bounds total operations to four, including retained successes. Every command retains the existing time/output bounds.

Legacy/versionless history remains readable but cannot resume because absence of a pending marker was not guaranteed historically. Pending dispatch with no durable result may already have caused side effects: resume refuses it rather than replaying it. Failed/cancelled command results and all-complete records also refuse resume. Explicit Retry remains a full restart, with its own consent, and may repeat checks. Interrupted dependency resolution whose metadata changed still fails closed and can require a new output folder. Reopening never starts commands automatically. These controls are for the existing trusted starter and single application session, not arbitrary project execution or a cross-process lock.


## Saved fixed execution limits

New outcomes and dispatch checkpoints include `limits` policy version 1: `commandTimeoutSeconds: 180`, `outputLimitBytes: 65536`, `maximumOperations: 4`. Native dispatch passes the saved deadline and output cap to the helper; the helper accepts only its fixed 180-second deadline and output cap. The validated four-operation graph includes retained successful steps during resume. These values are evidence of the fixed adapter policy, not user-configurable permissions. Unsupported versions, altered values, missing/extra members and wrong types inside an explicit policy fail closed when history is read. Historical records without the entire `limits` field infer the same policy that their runner used; this does not add missing historical checkpoints or establish a command result. Copying and saving such a record makes that policy explicit. Existing consent and all source/approval/resume guards still apply.


## Model source review

From a saved generated outcome, **Review model source proposal** selects a currently approved mapped board task and 1–8 recorded lib/test Dart files. The native snapshot service validates paths, recorded hashes, UTF-8 and size bounds before configured local-model inference. The review screen displays exact task/approval identity, a selectable line comparison, and full original/replacement text. `-` and `+` identify removed/added lines; numbered columns identify original/replacement positions. Explicit LF/CRLF/CR/no-newline markers expose terminator-only changes. Comparison uses bounded alignment after common-edge trimming; oversized changed regions are labeled as complete removal/addition, not a minimal edit sequence. Approval withdrawal/change hides retained review evidence. Cancellation suppresses late results but may not stop server-side inference immediately.

Review can explicitly prepare a separate unverified candidate copy; it grants no execution or promotion permission. Saved builds, project source and preview remain unchanged. Preparation alone grants no execution permission. Explicit candidate verification and promotion are described below.


### Isolated source candidate preparation

`prepareSourceCandidate` can prepare an unverified source copy after caller-obtained consent for a candidate parent. It requires exact current approval/mapped-task provenance and matching generated project input hashes throughout asynchronous work. Captured recorded files are hash checked; replacements must match their full captured originals. Only an OS-created unique folder outside the original receives writes. The original source/build/preview and saved generation are retained. The candidate starts with fresh hashes and current approval/task graph, with no old successful steps, compiled output or resolution state. No generated code is executed by preparation.

Capture is bounded to 64 files, 512 KiB/file and 2 MiB total, 16 path components and 128 source directories. Unrecorded, changed, missing, linked, unsafe or unexpected hidden paths refuse; only .gitignore is allowed as a hidden source file. Build, .dart_tool and pubspec.lock are excluded. Cancellation/approval failures refuse publication; partial candidate paths are reported and retained, with no automatic recursive deletion. These path checks do not isolate hostile concurrent same-user filesystem changes. Web reports unsupported. The review screen offers Select candidate parent folder, followed by a separate Prepare unverified candidate confirmation naming the destination. Preparation is controller-owned, prevents duplicate work, rechecks durable approval and cancellation, and displays the retained unverified path. The path is session-only; closing the screen does not delete copies or persist them as working output. Errors preserve service-reported partial paths. Candidate verification checkpoints are saved separately; explicit verification and promotion follow below.


### Confined candidate verification and explicit promotion

Prepared candidates carry additive `confinementVersion: 1`. Verification of these snapshots (including host-level checks of promoted snapshots after restart) always selects the macOS confined helper; unsupported hosts fail closed. After reviewing the full source diff, select **I approve confined candidate verification**, then **Verify candidate in sandbox**. The existing current approval, mapped task graph, working-generation identity and input fingerprints are rechecked before execution and across progress/save boundaries. Exact source/resolution fingerprints guard each command. Ordinary candidate verification adds no model retries; reviewed repair application with explicit consent is described below. Build Retry/Resume refuses an already promoted model snapshot; prepare a separate candidate for further checks so the working preview cannot be stopped by an in-place retry.

The trusted Python supervisor runs the initialized Dart/Flutter tools snapshot through `/usr/bin/sandbox-exec` with an inherited deny-by-default profile. Only the candidate and a per-command temporary directory are writable. SDK/package content is read-only; Pub bookkeeping uses a candidate-local overlay. Private home-file contents, outside writes, external sockets, arbitrary Mach lookups and signals to unrelated processes are denied. System runtime directories and required log/preferences/trust services are readable/available; metadata reads and loopback networking are allowed for Flutter test services. Environment credentials are not inherited; HOME/TMPDIR point to isolated temporary locations. The trusted supervisor holds the existing SDK cache lock without passing its descriptor to commands. Missing initialized SDK artifacts/cached dependencies fail; no downloads occur. The profile also denies SYS_setsid, SYS_setpgid and SYS_posix_spawn: descendants cannot escape the owned process group through session/group calls or spawn attributes. Normal fork/exec remains available to the cached SDK. The four approved operations retain the 180-second/64 KiB bounds and process-group cancellation. This is a macOS development confinement boundary, not a general adversarial VM, cross-platform sandbox or resource-quota system; trusted SDK/Python/cache contents and the same-user host application are outside it.

SourceCandidateController writes `studio.sourceCandidate.v1.<projectId>` checkpoints and results without touching the working-generation record or its preview. Closing review stops owned verification and retains candidate files/evidence. Candidate histories are inspectable evidence; this UI does not resume an interrupted candidate across restart, and no uncertain side effects are replayed. Prepare a fresh reviewed candidate after a failed/changed-input attempt if an explicit retry refuses.

Only a fully Ready candidate exposes **Promote verified candidate and refresh preview**. A separate host validates source and compiled-output fingerprints and starts a token-scoped preview while the old server remains active. ConditionalRecordStorage then atomically checks the working record and project/requirements/prototype/chat/approval snapshots and writes both the candidate working pointer and previous-working backup. No in-place source overwrite occurs. A preview/validation/approval/storage failure closes only the new preview and retains the original durable pointer, source folder and live preview. The commit is the publication point and cannot be cancelled once dispatched; after success the Build controller owns the new preview, and the previous host is retired. The old folder and its metadata backup remain available. This is not F06's user-selectable build-history/rollback feature. Candidate previews include a restrictive self-origin Content-Security-Policy; they remain separate browser origins from ASG.

## Candidate failure diagnosis (F05 first increment, issue #94)

Candidate verification displays read-only triage derived from the existing generated-project evidence. A normal nonzero analyze/test/build exit supplies a possible source-diagnosis input, with the exact operation/result/output retained; it does not prove source causation. Cancellation, deadline/output exhaustion, offline dependency resolution, signal termination, validation/runner refusal, pending unknown commands, interruption and unsupported/inconsistent history have separate intervention messages. Running progress, prepared candidates and successful verification do not display a failure diagnosis. No record schema/key changes or new execution permission.

The diagnosis itself starts no model request, command or source modification and cannot promote a candidate. Subsequent reviewed repair proposals use saved actual failure evidence and durable maximum-three request budgets per category and approval. Explicitly consented automatic repair sessions now request corrections for selected recorded Dart files, prepare each diff in a separate candidate under the selected parent, and rerun the complete confined check graph. The durable three-request limit applies independently to analyze/test/build for the exact approval (at most nine session iterations); failed/interrupted requests count. The loop stops on success, exhaustion, cancellation, stale authority or integration errors. No automatic promotion or restart replay occurs; a new session requires fresh consent. Live-model repair acceptance remains pending F05.


### Applying a reviewed repair and rerunning checks

After requesting a repair proposal, review its full diff and select a candidate parent folder. **I approve applying this repair and confined checks** enables **Apply reviewed repair and rerun checks** for that exact proposal. This creates a new separate candidate, then automatically reruns the complete approved offline resolve/analysis/test/web-build graph through the existing macOS sandbox, deadlines and output limits. Unsupported hosts fail closed. Ordinary proposals retain separate preparation and verification. The repair action makes no additional model request and does not promote output; promotion still requires its explicit action after actual successful checks.

The controller stays busy across preparation and dispatch and rechecks approval, working-record identity and cancellation after progress notification. Stop during copy prevents checks; Stop during checks uses the host cancellation and durable actual-exit handling. Copy/check failures preserve working output and saved prior runs. Actual rerun exits are stored in the candidate verification journal, including failure/uncertain states; no proposal or successful copy implies successful verification. A new repair request remains a separately reviewed action and consumes the existing per-category budget. This is not yet a fully automatic multi-attempt model repair loop.
